# Migrating Apps from Fly.io to oort / kuiper

Move a live Fly.io service onto `~/src/oort` (`github.com/dvcrn/k8s`) by staging on `${cluster}.<domain>` before cutting the app's hostname over.

Read `~/src/oort/.agents/skills/host-app/SKILL.md` for manifest shapes (overriding its `kuiper` and `ghcr.io/dvcrn/<app>` defaults: live Fly migrations target `oort` directly with Flux image automation on `ghcr.io/digitalvibeshq/<app>`) and [references/examples.md](references/examples.md) before editing probes, release workflows, or DNS cutover commits. For Elixir/Phoenix apps, load `migrate-to-otel-elixir` if `:new_relic_agent` is present, otherwise `install-otel-elixir`.

## Procedure

1. **Audit real state and `fly.toml` config before provisioning storage.**
   - Inspect `fly.toml` (`[env]`, `[[mounts]]`), `Dockerfile`, `priv/repo/migrations/`, and `rg "Repo\." lib/`. Carry required non-secret `[env]` entries (such as `DATABASE_PATH`) into `deployment.yaml`.
   - If zero migrations and zero `Repo` queries exist (unused `phx.new` SQLite scaffolding), delete `Repo`, `ecto_sql`, `ecto_sqlite3`, `DATABASE_PATH`, `rel/overlays/bin/migrate`, and `Dockerfile` `VOLUME` entries; keep `{:ecto, "~> 3.13"}` if embedded schemas or changesets remain, and deploy stateless with no `pvc.yaml` (zero-downtime cutover).
   - If real SQLite state exists on Fly, configure `pvc.yaml` + `strategy: {type: Recreate}` + `initContainers` migrations per `host-app`, stage with an empty or test DB in Step 4, and agree on a brief write-freeze window during Step 6 to copy a clean snapshot (`sqlite3 <db> ".backup /tmp/backup.db"` on Fly -> `fly ssh sftp get` -> `kubectl cp` into the `oort` PVC). If the app uses Litestream, follow [Database - SQLite & Litestream](#database---sqlite--litestream) instead of `initContainers` migrations and `kubectl cp`.
   - Before any DB-related work or migration, back up from Fly: `fly ssh console -C "sqlite3 <db> '.backup /tmp/backup.db'"`, `fly ssh sftp get /tmp/backup.db /tmp/backup.db`, `test -s /tmp/backup.db`, then `PRAGMA integrity_check` and row counts. Run `fly status` first and wake a stopped `auto_stop_machines` app with an HTTP request, or `sftp` prints `fly status` and `sqlite3` silently creates an empty local DB.
   - Stateful PVCs use `storageClassName: local-path-retain`. Check it exists (`mise -C ~/src/oort x -- kubectl --context <cluster>-ts get storageclass`); if missing, wire the manifest from `~/src/oort/infrastructure/storage/` in via a `storage` Flux Kustomization in `clusters/<cluster>/infrastructure.yaml` plus `dependsOn: [storage]` on `apps` in `clusters/<cluster>/apps.yaml`. If no retain class can be enabled, stop the migration.
2. **Purge Fly-only runtime wiring and harden kubelet HTTP probes.**
   - Remove `DNSCluster` (`FLY_APP_NAME.internal`), Fly IPv6 node naming in `rel/env.sh.eex` (`RELEASE_NODE`, `ECTO_IPV6`), and `FLY_*` / `NEW_RELIC_*` runtime config and `fnox.toml` keys. Treat `""` as unset when reading `ENV RELEASE_VERSION=""` in `config/runtime.exs`.
   - Keep `fly.toml` and `.github/workflows/fly-deploy.yml` intact until Step 6 so `main` stays deployable on Fly while staging.
   - Ensure an unauthenticated health endpoint exists (such as `/health`). Because kubelet hits the pod IP over plain HTTP without `X-Forwarded-Proto: https`, exclude the health path in `config/prod.exs` (`force_ssl: [rewrite_on: [:x_forwarded_proto], exclude: [paths: ["/health"], hosts: ["localhost", "127.0.0.1"]]]`); use `httpHeaders: [{name: X-Forwarded-Proto, value: https}]` on probes only when app code cannot be modified, or Phoenix returns `301` (`ProbeWarning`).
   - Also check the router and endpoint for canonical-host redirect plugs that `301` when `Host` != `PHX_HOST` (kubelet sends `Host: <pod-ip>`); mount `/health` in a router scope outside those pipelines, or exclude `/health` in the plug itself when it sits in `endpoint.ex`.
   - Set `initialDelaySeconds: 5` on `readinessProbe` (and `initialDelaySeconds: 15` if adding `livenessProbe`) so BEAM/Bandit startup (~3-4s) does not emit `Unhealthy: connection refused` on rollout.
3. **Move the repo to `digitalvibeshq` and publish `0.1.0` before deploying `apps/<app>`.**
   - Ask before transferring repo ownership. Once approved, transfer `dvcrn/<app>` to `digitalvibeshq/<app>` (`gh api repos/dvcrn/<app>/transfer -f new_owner=digitalvibeshq` and `git remote set-url origin ...`) so workflows can use the `kuiper` ARC runner scale set.
   - Add `.github/workflows/release.yml` triggered on `tags: ["[0-9]+.[0-9]+.[0-9]+"]` using `runs-on: kuiper`, `docker/setup-buildx-action@v4` (`driver: remote`, `endpoint: tcp://buildkitd.buildkit.svc.cluster.local:1234`, no `cache-from`/`cache-to`), and `platforms: linux/arm64` pushing `ghcr.io/digitalvibeshq/<app>:{{version}}`.
   - Merge the app PR, tag `0.1.0` on `main`, and wait for `release.yml` to push `ghcr.io/digitalvibeshq/<app>:0.1.0` before deploying `apps/<app>` in `dvcrn/k8s` (avoids `ImagePullBackOff` and Flux `ImageRepository` `NAME_UNKNOWN`).
4. **Create 1Password secrets and `~/src/oort/apps/<app>/` staged on `${cluster}.<domain>`.**
   - Run `env -u OP_SERVICE_ACCOUNT_TOKEN op ...` when checking or creating `vaults/k8s-oort/items/<app>` so a stale ambient service-account token does not return `403`. Follow `host-app` placeholder rules (never pass plaintext secrets on CLI arguments) and pause until the user fills real values, preserving Fly's existing `SECRET_KEY_BASE` / signing / encryption keys so cookies and data survive cutover.
   - Copy only Fly secrets the code still reads: `rg` each name from `fly secrets list` and drop the dead ones. Pipe values from `fly ssh console -C env` through `jq -R` into an `op item create` template on stdin without printing them; secrets copied this way need no placeholder pause.
   - Write `apps/<app>/` per `host-app` with `image: ghcr.io/digitalvibeshq/<app>:0.1.0 # {"$imagepolicy": "<app>:<app>"}` and `spec.image: ghcr.io/digitalvibeshq/<app>` in `image.yaml`.
   - Point OTLP at the in-cluster Alloy collector (`OTEL_SERVICE_NAME=<app>`, `OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf`, `OTEL_EXPORTER_OTLP_ENDPOINT=http://alloy.alloy.svc.cluster.local:4318`) with zero Axiom tokens in app pods.
   - Stage first on `fqdn: ${cluster}.<domain>` in `tunnelbinding.yaml` and `PHX_HOST: ${cluster}.<domain>` in `deployment.yaml` while `<domain>` remains on Fly.
   - For an app on a subdomain (`<sub>.<zone>`), stage on `${cluster}-<sub>.<zone>`, because Universal SSL does not cover the two-level `${cluster}.<sub>.<zone>`. When several apps share a zone, add `~/src/oort/infrastructure/cloudflare/clustertunnel-<zone>.yaml` (listed in that directory's `kustomization.yaml`) instead of an app-local `clustertunnel.yaml` (reuse it if it exists), and point `tunnelbinding.yaml` at it with `tunnelRef: {kind: ClusterTunnel, name: ${cluster}-<zone-with-dashes>}`.
5. **Verify staged deployment on `oort`.**
   - Push or merge the `dvcrn/k8s` change once confirmed, run `mise -C ~/src/oort x -- flux --context oort-ts reconcile kustomization apps -n flux-system --with-source`, and verify `0` `Unhealthy` or `ProbeWarning` events (`kubectl --context oort-ts -n <app> get events`), `HTTP/2 200` on `https://<staging-host>/health`, working WebSockets, and `trace_id`/`span_id` logs in Axiom.
6. **Cut over the app's hostname and clean up.**
   - Prepare two local commits without pushing: (a) in `~/src/oort`, change `fqdn` and `PHX_HOST` from the staging host to `<domain>`; (b) in the app repo, `git rm .github/workflows/fly-deploy.yml`. For stateful apps without Litestream, freeze writes on Fly and copy the `.backup` SQLite snapshot into the `oort` PVC now.
   - Ask the user to delete Fly's `A`/`AAAA` (or `CNAME`) records for `<domain>` in Cloudflare; for a subdomain like `esim.d.sh` these are the subdomain's own records, not the zone apex. Do **not** remove Fly's TLS certificate (`flyctl certs remove`) before those records are deleted, or Cloudflare Full (Strict) TLS serves `525` errors during cutover.
   - Push both commits immediately after confirmation, reconcile Flux `apps`, and verify `https://<domain>/health` hits the `oort` pod (`x-request-id` in `kubectl logs`).
   - Ask the user to delete the orphaned staging-host `CNAME` and `_managed.<staging-host>` `TXT` records (left behind by in-place `TunnelBinding` `fqdn` edits) plus Fly's `_acme-challenge` / `_fly-ownership` records in Cloudflare. Leave `fly.toml` and the Fly app intact for rollback until the user asks to destroy it.

## Database - SQLite & Litestream

Applies only when the app replicates SQLite with Litestream. Read example 5 in [references/examples.md](references/examples.md) before editing the start script or seeding R2.

- Pin the image (`COPY --from=litestream/litestream:<ver>`), never `:latest`: 0.3 and 0.5 replica formats are incompatible, and a typical start script boots an empty DB when restore fails. Check Fly's version (`fly ssh console -C "litestream version"`) and pin the latest patch of that minor line (Fly on 0.5.x -> latest 0.5.x, never across 0.3/0.5).
- Replicate to a new Cloudflare R2 bucket `<app>-litestream` in account `02c07a2514d9a25f58c78a180bb8c6f3` (endpoint `https://<account>.r2.cloudflarestorage.com`, region `auto`), never to the replica Fly still writes (two writers corrupt it). R2 over Tigris: 1M free Class A ops/month vs 10k, and no Fly account dependency.
- Put R2 keys (Object Read & Write, scoped to the bucket) in the app's `k8s-oort` 1Password item as `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY`; bucket, endpoint, and region are plain env in `deployment.yaml`.
- Pods run as UID 65534, so the start script writes `litestream.yml` under `/tmp`, not `/etc`. The deployment needs `strategy: {type: Recreate}`, `fsGroup: 65534`, the PVC on `local-path-retain`, and `livenessProbe.initialDelaySeconds: 30` because restore runs before boot.
- Drop `initContainers` migrations: a migrate step on an empty PVC creates the DB file, so `restore -if-db-not-exists` skips R2. Run migrations in the app after restore (`Ecto.Migrator` in the supervision tree).
- Seed R2 from the verified Step 1 backup before the first deploy: run the pinned image locally with `replicate`, wait for `snapshot complete`, stop it, then `restore -if-db-not-exists` into an empty dir and compare row counts. Pass credentials as `-e NAME` from env (`op read`), never as literal values. The first pod on an empty PVC restores from R2.
- Never purge or re-seed R2 while the app's pod is running or can start: a pod that restores mid-seed or writes during a purge leaves a mixed replica history that cannot be trusted to restore. To re-seed after `apps/<app>` is applied, scale the deployment to 0, purge `<bucket>/<db>`, delete `.<db>-litestream` on the PVC (or the PVC itself), seed, then scale to 1. Purge with `rclone purge` (S3 env config); `aws` may be an unconfigured mise shim.
